# Keycloak realm in Terraform (`infra/keycloak`)

Terraform that builds the identity-stack realm in a Keycloak: the same realm the compose
services import from [`keycloak/realm/identity-stack-realm.json`](../../keycloak/realm/identity-stack-realm.json).
It uses the `keycloak/keycloak` provider (`~> 5.10`) and `hashicorp/random` (`~> 3.6`).

It targets the local compose container. There is no hosted Keycloak; adding one is an owner
decision recorded in the Keycloak epic. State is local (`terraform.tfstate` in this directory)
and git-ignored; `.terraform.lock.hcl` is committed.

## What it creates

| Resource | What |
|---|---|
| `keycloak_realm.this` | The realm (default name `identity-stack-terraform`): Organizations on, registration off, unique emails, `verifyEmail` on, brute-force detection on with temporary lockouts (30 failures, wait growing from 60 s to 15 min), SSL mode `var.ssl_required` (`none` for the local container). |
| `keycloak_openid_client.type` | Type clients `member` and `tenant-admin`: confidential, no flows, full scope off. |
| `keycloak_role.client` | Their client roles, the permissions: `member` has `documents:read`, `documents:write`; `tenant-admin` has `members:invite`, `members:remove`, `settings:manage`. |
| `keycloak_openid_client.app` | App clients `member-app` and `tenant-admin-app`: public, standard flow only, PKCE `S256`, full scope off, redirect URI and web origin `var.frontend_url`, post-logout redirect `<frontend_url>/login`. |
| `keycloak_openid_client_default_scopes.app`, `keycloak_openid_client_optional_scopes.app` | App client scopes: default `basic`, `roles`, `profile`, `email`, `web-origins`, `acr`; optional `organization`, `offline_access`. |
| `keycloak_generic_role_mapper.app` | Scope mappings: each app client to its own type client's roles only. A token's `aud` is then that type client and its `resource_access` holds that type client alone. |
| `keycloak_user.this`, `keycloak_user_roles.this`, `random_password.user` | Users `alice`, `bob`, `carol`, `dave`, `erin`, `frank` with the import's emails, names and client roles. `keycloak_user_roles` is exhaustive: a user holds exactly the listed client roles and no realm role, as in the import. |
| `keycloak_organization.this` | Organizations `acme` (domain `acme.test`) and `globex` (`globex.test`). `acme` carries the attribute `type:tenant-admin` listing the ids of `bob`, `dave` and `frank`. |
| `keycloak_organization_memberships.this` | Members: `acme` has all six users, `globex` has `bob`. |
| `keycloak_openid_client.directory` and its scopes, roles and scope mappings | `identity-stack-directory`, the backend's read-only service account for the organization lookup: client scope `kc-admin-api`; its service account holds exactly `realm-management` roles `view-users` and `view-organizations` and no realm role (`keycloak_user_roles.directory`, exhaustive), as in the import. |

The root declares no protocol mapper. Keycloak's built-in client scopes write `aud`,
`organization` and `resource_access` from client roles and memberships, and Keycloak sets `azp`
itself; no mapper copies a user attribute or property into those claims, or into `dct` or
`tenants`.

Two things differ from the import, by necessity:

- **User ids.** The provider cannot set a user's id, so Keycloak picks them and a token's `sub`
  is not the import's fixed id. The output `user_ids` lists them.
- **Credentials.** The import's fixture passwords and client secrets are not repeated here.
  User passwords are generated (`random_password`) and the directory client's secret is
  generated by Keycloak. Both are sensitive outputs, kept in local state only. The type
  clients' secrets are never used (they have no flows) and are not output.

The backend's token model for the realm (`member` portable with `documents:read`,
`tenant-admin` organization-bound) is not part of the realm; it is in `local.type_clients` and
comes out in `backend_environment`.

## Run it

Start the compose Keycloak, then apply. The provider logs in to the `master` realm as the
bootstrap admin through `admin-cli`; the login comes from the environment, never from a tfvars
file. `admin`/`admin` is the compose container's local fixture login.

The realm must not exist before the apply. The compose `keycloak` service already imports a realm
named `identity-stack`, so the root's default realm is `identity-stack-terraform`, which sits
beside it. Against a Keycloak that did not import the realm, `-var realm=identity-stack` builds it
under the import's name.

```bash
docker compose --profile keycloak up -d --wait keycloak
cd infra/keycloak
export KEYCLOAK_USER=admin KEYCLOAK_PASSWORD=admin
terraform init
terraform apply
terraform output backend_environment
terraform output -raw keycloak_directory_client_secret
terraform output -json user_passwords
```

Variables (all have defaults for the compose `keycloak` service):

| Variable | Default | What |
|---|---|---|
| `keycloak_url` | `http://keycloak.localhost:8180` | The Keycloak's `KC_HOSTNAME`. The issuer is `<keycloak_url>/realms/<realm>`. `http://` only for a loopback or `*.localhost` host (validated). |
| `realm` | `identity-stack-terraform` | Realm to create; it must not exist yet. Not `identity-stack` beside the compose import, which already has that name. |
| `frontend_url` | `http://localhost:3000` | SPA origin: redirect URI, web origin, post-logout `<frontend_url>/login`. A bare origin, `scheme://host[:port]`: no path, query or trailing slash; `http://` only for a loopback or `*.localhost` host (both validated). |
| `ssl_required` | `none` | Realm SSL mode. `none` only when `keycloak_url` is a loopback or `*.localhost` host (validated); set `external` or `all` for any other Keycloak. |

## Outputs

| Output | Feeds |
|---|---|
| `backend_environment` | Backend `KEYCLOAK_ISSUER_URL`, `KEYCLOAK_AUDIENCES`, `KEYCLOAK_APP_CLIENTS`, `KEYCLOAK_PORTABLE_TYPES`, `KEYCLOAK_ORGANIZATION_BOUND_TYPES`, `KEYCLOAK_PORTABLE_PERMISSIONS`, `KEYCLOAK_REQUIRE_HTTPS`, `KEYCLOAK_POST_LOGOUT_REDIRECT_URI`, `KEYCLOAK_DIRECTORY_CLIENT_ID` ([`docs/environment-variables.md`](../../docs/environment-variables.md)). |
| `keycloak_directory_client_secret` (sensitive) | Backend `KEYCLOAK_DIRECTORY_CLIENT_SECRET`. |
| `frontend_environment` | Frontend `VITE_OIDC_AUTHORITY`, `VITE_OIDC_CLIENT_ID`, `VITE_OIDC_REDIRECT_URI`, `VITE_OIDC_SCOPE`, one map per app client. The scope is `openid profile email organization`: `organization` is optional on the app clients, and without it the token carries no `organization` claim, so an organization-bound type (`tenant-admin`) is refused. Keycloak asks a member of several organizations which one to use. |
| `user_ids` | Each user's id (token `sub`). |
| `user_passwords` (sensitive) | Each user's login password. |

## Members added by hand are removed

`keycloak_organization_memberships` is authoritative over an organization's members. A member
added to `acme` or `globex` in the admin console or through the Admin API shows up as a change in
the next `terraform plan`, and the next `terraform apply` removes them. Add members here instead.
`keycloak_user_roles` is authoritative in the same way over each user's roles.

## Keeping it the same as the import

When a change adds a user, client, role, organization or member to the import file, the same
change adds it here. `make keycloak-terraform-check`
([`scripts/check-against-compose.sh`](scripts/check-against-compose.sh)) checks the two against
each other in the compose `keycloak-test` container. The `identity-stack` realm there is the
import from when the container was created; after a change to
[`keycloak/realm/identity-stack-realm.json`](../../keycloak/realm/identity-stack-realm.json),
recreate it with `make test-down && make test-up-keycloak`, as a failed comparison says. The check:

1. deletes any `identity-stack-terraform` realm an earlier killed or failed run left behind,
   then applies this root to a new realm of that name beside
   the imported `identity-stack`, with its own state in a new directory under
   `${XDG_CACHE_HOME:-~/.cache}/identity-stack-keycloak-terraform-check/`;
2. runs `terraform plan` again and fails unless it is empty;
3. runs [`scripts/check_realm.py`](scripts/check_realm.py), which compares, in both
   directions, the realm settings, every client (Keycloak's built-in ones by name only), client
   roles, scope mappings, the directory service account's client and realm roles, every user and
   their client and realm roles, organizations, domains, members and `type:` attributes through
   the Admin API; logs the users in to both realms and compares
   the tokens' `iss`, `aud`, `azp`, `organization`, `resource_access`, `scope` and claim names;
   compares the claim names with [`keycloak/fixtures/access-token.json`](../../keycloak/fixtures/access-token.json);
   fails on any protocol mapper that writes a user attribute or property to `aud`, `azp`,
   `organization`, `resource_access`, `dct` or `tenants`; logs in through each app client with
   the output `VITE_OIDC_SCOPE` and fails unless the token names the user's organization; and reads `bob`'s organizations
   with the directory client's generated secret. Users, organizations and members are read
   one page of `LISTING_PAGE_SIZE` at a time, and a full page fails the check as possibly cut off;
4. with `--integration-tests` (`make keycloak-terraform-integration`), runs the backend's
   Keycloak integration tests (`backend/tests/integration/test_keycloak_*.py`) against the
   built realm, logging in with the generated user ids and passwords and asking the directory
   with its generated secret (`backend/tests/helpers/keycloak_target.py`). They need the rest of
   the test stack up and, for one test, a Descope client (`DESCOPE_PROJECT_ID`,
   `DESCOPE_CLIENT_ID`, `DESCOPE_CLIENT_SECRET`, read from `backend/.env` when present);
5. destroys the realm. The run's state directory holds the generated passwords and directory
   secret and is deleted, except when the destroy failed: then it is kept and its path printed.
   The next run deletes the realm (step 1) and then every state directory an earlier run kept
   or was killed with.

The comparison covers the fields the import file uses today, listed at the top of
`check_realm.py` (`REALM_SETTINGS`, `CLIENT_SETTINGS`, `CLIENT_ATTRIBUTES`, `USER_SETTINGS`). A
change that makes the import use a field outside those lists (a user attribute, a required
action, another client attribute, a realm role or a group) adds the field to the list in the
same change; the check does not notice an uncompared field by itself.

It copies only the root's `.tf` files git does not ignore into its working directory, so a local
`override.tf` or `*_override.tf` never changes what it applies.

It needs `terraform`, `curl`, `jq` and the backend virtual environment
(`cd backend && uv sync --locked --extra dev`), and checks for each before it does anything.
Neither the script nor `make keycloak-terraform-check` starts, stops or removes keycloak-test:
bring it up first with `make test-up-keycloak`; the script fails when it is not answering. It runs on Linux. CI
runs it on every pull request (the `keycloak-terraform-check` job in `.github/workflows/ci.yml`),
so a change to the import file without the matching change here fails the pull request. Two runs against one keycloak-test at the same time are not supported: where several
sessions share a Docker host, serialise them (for example with `flock`).
