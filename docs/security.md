# Security

This documents the application-level security controls. For vulnerability reporting see [`../SECURITY.md`](../SECURITY.md).

## Token validation

Bearer tokens are validated by [`py-identity-model`](https://github.com/jamescrowley321/identity-model) (the 5.0.0 pre-release, pinned to one commit of its repository; it enforces a provider's signing-algorithm allowlist and pulls `cryptography>=50` with the PYSEC-2026-3552/3553/3554 fixes). Validation accepts all three Descope issuer formats, all signed by the same project JWKS. The library checks a token's `iss` against the three (`TokenValidationConfig.token_issuers`, set by `library_token_issuers()` in `middleware/providers.py`) and uses them only with the keys of a discovery document whose own issuer is one of them; every other provider's tokens must carry its discovery issuer:

- `https://api.descope.com/{project_id}` — OIDC / ID tokens
- `https://api.descope.com/v1/apps/{project_id}` — OIDC inbound-app tokens
- `{project_id}` — the **bare project id**, used by SDK / session / access-key tokens (e.g. the `sessionJwt` from the access-key exchange endpoint)

When `ORY_ISSUER_URL` is set, Ory access tokens are accepted too: one issuer, with the audience enforced unless `ORY_REQUIRE_AUDIENCE` is off (`middleware/providers.py`).

In `gateway` mode, Tyk verifies the token signature at the edge. The backend's `GatewayClaimsMiddleware` decodes the forwarded JWT without re-checking the signature, and still checks expiry, issuer, signing algorithm, audience and sender constraint as defence in depth (`middleware/factory.py`, `middleware/claims.py`).

### Signing algorithms

Every provider accepts RS256 only (`ProviderTokenConfig.algorithms` in `middleware/providers.py`). A token signed with any other algorithm is answered 401, even when its key is published in the provider's own JWKS and the signature would verify. `POST /api/validate-id-token`, which runs behind neither middleware, validates the token as an OIDC ID token with the config of the configured provider whose issuer is the token's `iss` (Descope's ID tokens: its two `https://api.descope.com/` issuers, each against its own discovery document), with that provider's algorithms and the SPA's client id as `aud` and `azp`. An `iss` no provider has, an access token (it carries `scope`, or has no `azp` among several audiences) and any refused token get the same 401. When the token cannot be judged at all, because the provider's discovery document or JWKS cannot be fetched or is unusable, or the provider config is refused (plain HTTP where HTTPS is required, or no client id to check `aud` against), it answers 503 `{"detail": "Identity provider unavailable"}` and logs the cause at ERROR. Its log lines name the error type only, never the library's message, which quotes the token's header.

| Provider | Accepted | Basis |
|---|---|---|
| Descope | RS256 | The project's JWKS publishes one RSA key with `alg: RS256`, and its discovery document advertises RS256 only. |
| Ory | RS256 | Ory Network and a default Hydra sign access tokens with RS256 keys. |
| Keycloak | RS256 | Project policy for the realm. |

In `standalone` mode the library enforces the set on the token's header `alg` (RFC 8725 §3.1). In `gateway` mode the backend never calls the library, so `GatewayClaimsMiddleware` applies the same set to the header itself.

No environment variable changes the set. An Ory Network project or a Hydra deployment configured to sign access tokens with another algorithm (ES256, for example) has every token refused with 401 until that algorithm is added to the set in `ory_config()`; a Descope project's set is in `descope_config()` and a Keycloak realm's in `keycloak_config()`, all in `middleware/providers.py`. In `gateway` mode the gateway has to verify signatures of that algorithm as well.

Independently of the set, the library accepts no HMAC algorithm and no unsigned token.

### Sender-constrained tokens

The backend accepts bearer tokens only. An access token bound to a DPoP key (`cnf.jkt`, RFC 9449) or to a client certificate (`cnf["x5t#S256"]`, RFC 8705) is valid only with its proof or its certificate, and the backend checks neither, so a bound token is answered 401 in both modes. In `standalone` mode the library refuses it (RFC 9449 §7.2). In `gateway` mode the gateway's JWT check does not read `cnf`, so `GatewayClaimsMiddleware` refuses it (`sender_constrained()` in `middleware/providers.py`).

## Authorization (RBAC + FGA)

Route handlers enforce authorization with dependency guards built over the validated claims:

- `require_role(...)` — role checks against the token's `tenants`/`dct` claims, or against the canonical model for providers in `CANONICAL_RBAC_PROVIDERS` (`dependencies/rbac.py`).
- `require_permission(...)` — permission checks, resolved the same way.

A Keycloak principal is authorized from the canonical model, as Ory and Zitadel principals are, once `keycloak` is listed in `CANONICAL_RBAC_PROVIDERS`: its tenant, roles and permissions are the canonical ones, and no claim on its token (`resource_access`, `realm_access`, `roles`, `dct`, `tenants`) grants anything. The token is first held, at authentication and on every route, to an RS256 signature from the realm, the configured issuer, the API client (`KEYCLOAK_AUDIENCE`) in `aud`, the SPA client (`KEYCLOAK_CLIENT_ID`) as `azp`, and `typ` `Bearer`, so the SPA's ID and refresh tokens and every other client's tokens get 401. A canonical user who is not active is refused (403) whatever their token. See [architecture.md](architecture.md#keycloak-principals), [ADR-0011](adr/0011-keycloak-canonical-authorization.md) and [conventions §18](conventions.md#18-one-resolver-decides-the-tenant-and-the-grants).

Keycloak principals are provisioned just in time only when an operator adds `keycloak` to `JIT_ENABLED_PROVIDERS`. A first sign-in joins, as `member`, the one active tenant linked (`tenants.external_org_id`, for the `keycloak` provider) to the one alias in the token's `organization` claim, with the email and names from the access token. No claim, two aliases, an alias no tenant names, or a missing or unverified email provisions nothing. It follows the rules of every organization-placed first login described for Zitadel below: never linked to an existing canonical user by email, and only for an email in the tenant's `domains`. A realm used here must still keep `email_verified` meaningful: it must not broker another identity provider whose email it takes on trust, must not let users register themselves, must keep emails unique, and must verify an email before it counts (`verifyEmail` on). The compose realm does all four, and `tests/integration/test_keycloak_canonical.py::test_the_realm_keeps_email_verified_meaningful` reads them back from it.

With `SYNC_PROVIDER=keycloak` the canonical model and the realm are kept in two-way sync ([keycloak.md](keycloak.md#admin-adapter)), which makes the realm's administrators an authority over it. The backend pushes every canonical tenant, user, membership, permission, role and role assignment to the realm with one service account, `identity-stack-admin`, which holds `manage-users`, `manage-organizations`, `query-clients` and `view-events` and fine-grained permissions on the API client alone, so it cannot change the SPA client's redirect URIs or any other client. What an administrator changes in the realm comes back at the next poll of its admin and user events (`KEYCLOAK_PULL_INTERVAL_SECONDS`, 10 s by default) and at each reconciliation pass: an account disabled or deleted deactivates its canonical user, an organization membership or role group membership added or removed assigns or removes the role, an organization disabled suspends its tenant, and API client roles and composites become permissions and roles. Anyone who can administer the realm's users, organizations or the API client can therefore grant any canonical role in any tenant linked to it; hold the realm's administration to the same standard as the backend's database. A revocation in the console takes effect at the next poll, not at once: a disabled account's unexpired token is served until then. A user's own account changes (self-service profile and email) carry no grant, and their email comes over only once Keycloak has verified it, marked `email_from_organization` so no first login links to it. Events the service account wrote are the backend's own pushes and are not applied again. A canonical change that is not yet delivered to the realm (`pending_pushes`) is not overwritten by reconciliation, so a console change the poll missed loses to it.

Zitadel principals are provisioned just in time only when an operator adds `zitadel` to `JIT_ENABLED_PROVIDERS`. A first login joins, as `member`, the one active tenant linked to the token's organization, and takes its email from UserInfo. It is never linked to an existing canonical user by email, verified or not, because the trust root there is not one administrator: every tenant organization's administrators can create a user with any email and mark it verified. If email linking were allowed, an administrator of one tenant could take over another tenant's admin. Nor does it create a user for an email outside its tenant's `domains` (whole domain; an email with more than one `@`, an empty domain, or a domain with an upper-case letter or ending in `.` is outside them, because the lookup by email is exact; a tenant with none admits no first login), so an organization's administrators can only take emails of their own tenant's domains. A Descope reconciliation run leaves the `domains` of a tenant linked to an organization as they are, so a Descope tenant of the same name cannot widen or clear them. A first login whose email is outside those domains, or held by a canonical user, gets the 403 an unlinked organization gets, and nothing is written. That one answer hides which refusal fired and anything about emails outside the tenant's domains, but within those domains a 403 where a free email gets 200 still tells an organization administrator who chose the email that a canonical user holds it; an administrator links such a user beforehand with an `idp_links` row. The refusal is logged at warning with the id of the user holding the email, or of the tenant, never the email. Nor is any other provider's first login (Ory, Keycloak, the Descope flow sync), or a Descope reconciliation run, linked by email to a user a Zitadel first login created (`users.email_from_organization`, shown in `GET /api/users`): that email was chosen by an organization's administrators, and linking it would let one of them pre-create the account another person's first login joins. It gets 409 with a body that names no cause. The cost is that such an administrator can squat the emails of their own tenant's domains: their first logins elsewhere are refused until an operator releases the email, as [zitadel.md](zitadel.md) describes. A tenant's organization link is matched for its own provider only (`tenants.external_org_provider_id`), so an organization id another provider uses is never read as a Zitadel organization. See [zitadel.md](zitadel.md) and [conventions §28](conventions.md#28-a-provider-is-one-registration).

`KEYCLOAK_REQUIRE_HTTPS=false` is accepted only for an issuer on `localhost`, a loopback address or a `.localhost` name. The check reads the name and does not resolve it. A `.localhost` name is reserved for loopback, but a resolver or hosts file that points one elsewhere is not detected, and the discovery document and signing keys would then be fetched from that host over plain HTTP. Leave HTTPS enforcement on outside local development and tests. The backend logs a warning at startup whenever it is off.

Both, and `get_tenant_id`, take the tenant and the grants from one resolver (`dependencies/tenant_access.py`, [conventions §18](conventions.md#18-one-resolver-decides-the-tenant-and-the-grants)). A principal from a provider in `CANONICAL_RBAC_PROVIDERS` who belongs to several tenants names one with the `X-Tenant-ID` request header. The header only chooses among the caller's own canonical memberships: a tenant outside them is answered with 403, and a Descope principal's tenant is always its `dct` claim, whatever the header says. No route hands another provider's tenant or `sub` to Descope. Descope's access keys are built only for a Descope principal (`require_descope_principal` in the `machine_credentials` builder, `dependencies/identity.py`); a canonical provider's machine credentials are canonical rows (Keycloak: clients the adapter registers), and a machine credential's token is authorized from that credential alone. A machine credential's token is refused (403) on every route that changes people's roles, memberships, credentials or relations: `/api/keys`, so no credential mints its successor; the role assignment, role and permission definition and member routes; the FGA relation and schema writes and a document's share and revoke; and the IdP-link writes ([ADR-0012](adr/0012-routes-speak-canonical.md)). The documents, FGA relations and FGA schema reach the deployment's relationship store, which serves only the principals whose ids it keys on (Descope FGA: Descope principals; OpenFGA: canonical principals); everyone else gets 404. The tenant settings and the profile's custom attributes go through the sync adapter's `custom_attributes` capability, which serves only that provider's own principals. `GET /api/tenants/current` reads a canonical principal's tenant from the canonical model and asks Descope only for a Descope principal's. The role and permission routes (`/api/roles`, `/api/permissions`, `POST /api/roles/assign` and `/api/roles/remove`) push every write to the configured sync adapter (`SYNC_PROVIDER`), so `require_sync_provider_principal` (`dependencies/sync_provider.py`) serves that provider's principals only: Descope's in a Descope deployment, Keycloak's or Zitadel's where the backend syncs to them. The member routes (`/api/members*`) are fenced the same way: in a Descope deployment they call Descope as before, and elsewhere they read and change the canonical members, whose changes the sync adapter pushes. An invitation only creates an account: an email any canonical user already has is refused (409) whichever tenant holds it, so it neither enrols nor describes another tenant's account. An invitation with `operator` is refused for a caller who is not an operator; a status change is refused for a member who also belongs to another tenant (409): the status is the account's. Changing the role and permission definitions is gated by `require_definitions_role`: a canonical principal needs `operator` by its sole membership, never a tenant's `admin`, since a tenant admin could otherwise delete the `owner` role in every tenant or grant the `member` role a permission everywhere; a Descope principal keeps `owner` or `admin` from its claims. Listing them, which changes nothing and shows only the global definitions, needs `owner`, `admin` or `operator` in the request's tenant. Only a caller who holds `operator` the same way (sole canonical membership, or Descope claims) can assign or remove `operator` through `POST /api/roles/assign` and `/api/roles/remove`; a tenant admin cannot make itself or anyone else an operator. Likewise only an operator can create, change, rename to or from, or delete the `operator` role definition. `GET /api/roles/me` answers any principal its roles and permissions in the resolver's tenant. The routes over state that belongs to no tenant and is not Descope's (`GET /api/users`, which lists every tenant's users, `/api/providers`, `/api/sync/status` and `/api/events/recent`) are gated by `require_global_role("operator")`. The request chooses nothing there: a canonical principal is served on the role of their sole membership, and one who belongs to several tenants is refused, whether they name one with the header, carry a `dct` claim on the token, or name none, so being an operator of one tenant among several does not open every tenant's data. A project-level grant for these routes is #593.

- `require_fga(...)` — fine-grained (ReBAC) authorization in the deployment's relationship store, Descope FGA or OpenFGA (`dependencies/fga.py`, `RELATIONSHIP_STORE`); an FGA error is answered with 502 and treated as a denial.
- `require_admin_role` — a plain dependency in `routers/tenants.py` that checks a Descope token's project-level `roles` claim for `owner` or `admin`; only `POST /api/tenants` uses it. It, and `get_tenant_claims` (the Descope `tenants` claim, which `get_tenant_memberships` reads for a Descope principal on `GET /api/tenants` and the `/api/tenants/{tenant_id}/resources` routes; a canonical principal's tenants come from the canonical model), take the claims from `get_descope_claims`, which refuses every principal whose provider is not Descope-managed (403), so those claims on a Keycloak, Ory or Zitadel token grant nothing.

Every tenant-scoped route must declare one of the first three, and a unit test enforces it ([conventions §15](conventions.md#15-every-tenant-scoped-route-declares-its-authorization)).

## Transport & request hardening

- **Security headers** — `SecurityHeadersMiddleware` sets response hardening headers; `ENVIRONMENT=production` adds HSTS and the strict default CSP (`CSP_POLICY` overrides the CSP).
- **Rate limiting** — [slowapi](https://github.com/laurentS/slowapi): `RATE_LIMIT_DEFAULT` (60/min) and `RATE_LIMIT_AUTH` (10/min for auth-sensitive routes); keyed by the authenticated `sub` or by client IP. `GET /api/health` is exempt. Standalone mode only: in `gateway` mode Tyk does the rate limiting.
- **Trusted proxies** — `TRUSTED_PROXY_HOSTS` controls which forwarded headers are honored.
- **Internal endpoints** — `/api/internal/*` are each gated by a shared secret; an unset secret makes the endpoint reject all traffic (fail-closed).

## Supply-chain / CI scanning

Security scanning runs in CI (`.github/workflows/`), using GitHub-native and FOSS tools:

- `codeql.yml` — CodeQL static analysis
- `osv-scanner.yml` — OSV dependency scanning
- `dependency-review.yml` — PR dependency review
- `scorecard.yml` — OpenSSF Scorecard
- `security.yml` — `pip-audit`, `npm audit`, gitleaks secret scanning and Semgrep (uploaded to code scanning)

Locally, `make security` runs `pip-audit` + `npm audit`.

## Notable dependency pins (decision record)

- **`fastapi>=0.115.0,<0.137`** — capped because slowapi 0.1.10's `SlowAPIMiddleware` route matcher only recognizes top-level routes under the newer FastAPI inclusion model, which breaks rate limiting. Revisit when slowapi ships a fix (`backend/pyproject.toml`).
- **`py-identity-model` 5.0.0 pre-release** — pinned to one commit of the library's repository (`git+https://github.com/jamescrowley321/identity-model@<sha>#subdirectory=py`) in `backend/pyproject.toml` and `backend/uv.lock`, because v5 pre-releases are not published to PyPI and each pre-release's assets are deleted when the next one is cut. The pinned commit carries `TokenValidationConfig.token_issuers` (identity-model#1184), which lets the library check a Descope token's `iss` against all three issuer forms; it moves to a `release/v5` commit once that change is merged there, and is replaced by `>=5.0.0,<6` when 5.0.0 is released (see Token validation above). The installed package reports version 4.1.1: the library sets its version at release time, so the commit, not the version, says what is installed. Installing it needs `git` (the backend image installs it for the build step and removes it). While the pin is a commit, dependency scanning does not cover this one package: `pip-audit` skips a package that is not on PyPI, and Dependabot proposes no update for a git source. Until the pin is a PyPI range, advisories and new commits for the library are followed on [its repository](https://github.com/jamescrowley321/identity-model/security/advisories), and a newer commit is taken by changing the sha in `backend/pyproject.toml`, then running `uv lock` and `uv sync --locked --reinstall-package py-identity-model`. Read `docs/upgrade-v5.md` at the new commit before taking it.
