# Keycloak realm in Terraform (`infra/keycloak`)

Terraform that builds the identity-stack realm in a Keycloak: the same realm the compose
services import from [`keycloak/realm/identity-stack-realm.json`](../../keycloak/realm/identity-stack-realm.json).
It uses the `keycloak/keycloak` provider (`~> 5.10`) and `hashicorp/random` (`~> 3.6`).

It targets the local compose container. There is no hosted Keycloak; adding one is an owner
decision recorded in the Keycloak epic. State is local (`terraform.tfstate` in this directory)
and git-ignored; `.terraform.lock.hcl` is committed.

## What it creates

| Resource | What |
|---|---|
| `keycloak_realm.this` | The realm (default name `identity-stack`): Organizations on, registration off, unique emails, `verifyEmail` on, SSL mode `var.ssl_required` (`none` for the local container). |
| `keycloak_openid_client.type` | Type clients `member` and `tenant-admin`: confidential, no flows, full scope off. |
| `keycloak_role.client` | Their client roles, the permissions: `member` has `documents:read`, `documents:write`; `tenant-admin` has `members:invite`, `members:remove`, `settings:manage`. |
| `keycloak_openid_client.app` | App clients `member-app` and `tenant-admin-app`: public, standard flow only, PKCE `S256`, full scope off, redirect URI and web origin `var.frontend_url`, post-logout redirect `<frontend_url>/login`. |
| `keycloak_openid_client_default_scopes.app`, `keycloak_openid_client_optional_scopes.app` | App client scopes: default `basic`, `roles`, `profile`, `email`, `web-origins`, `acr`; optional `organization`, `offline_access`. |
| `keycloak_generic_role_mapper.app` | Scope mappings: each app client to its own type client's roles only. A token's `aud` is then that type client and its `resource_access` holds that type client alone. |
| `keycloak_user.this`, `keycloak_user_roles.this`, `random_password.user` | Users `alice`, `bob`, `carol`, `dave`, `erin`, `frank` with the import's emails, names and client roles. `keycloak_user_roles` is exhaustive: a user holds exactly the listed client roles and no realm role, as in the import. |
| `keycloak_organization.this` | Organizations `acme` (domain `acme.test`) and `globex` (`globex.test`). `acme` carries the attribute `type:tenant-admin` listing the ids of `bob`, `dave` and `frank`. |
| `keycloak_organization_memberships.this` | Members: `acme` has all six users, `globex` has `bob`. |
| `keycloak_openid_client.directory` and its scopes, roles and scope mappings | `identity-stack-directory`, the backend's read-only service account for the organization lookup: client scope `kc-admin-api`, `realm-management` roles `view-users` and `view-organizations`. |

The root declares no protocol mapper. Keycloak's built-in client scopes write `aud`,
`organization` and `resource_access` from client roles and memberships, and Keycloak sets `azp`
itself; no mapper copies a user attribute or property into those claims, or into `dct` or
`tenants`.

Two things differ from the import, by necessity:

- **User ids.** The provider cannot set a user's id, so Keycloak picks them and a token's `sub`
  is not the import's fixed id. The output `user_ids` lists them.
- **Credentials.** The import's fixture passwords and client secrets are not repeated here.
  User passwords are generated (`random_password`) and the directory client's secret is
  generated by Keycloak. Both are sensitive outputs, kept in local state only. The type
  clients' secrets are never used (they have no flows) and are not output.

The backend's token model for the realm (`member` portable with `documents:read`,
`tenant-admin` organization-bound) is not part of the realm; it is in `local.type_clients` and
comes out in `backend_environment`.

## Run it

Start the compose Keycloak, then apply. The provider logs in to the `master` realm as the
bootstrap admin through `admin-cli`; the login comes from the environment, never from a tfvars
file. `admin`/`admin` is the compose container's local fixture login.

The compose `keycloak` service already imports a realm named `identity-stack`, and the realm must
not exist before the apply. Either give the Terraform realm another name, or start a Keycloak
without the import.

```bash
docker compose --profile keycloak up -d --wait keycloak
cd infra/keycloak
export KEYCLOAK_USER=admin KEYCLOAK_PASSWORD=admin
terraform init
terraform apply -var realm=identity-stack-terraform
terraform output backend_environment
terraform output -raw keycloak_directory_client_secret
terraform output -json user_passwords
```

Variables (all have defaults for the compose `keycloak` service):

| Variable | Default | What |
|---|---|---|
| `keycloak_url` | `http://keycloak.localhost:8180` | The Keycloak's `KC_HOSTNAME`. The issuer is `<keycloak_url>/realms/<realm>`. |
| `realm` | `identity-stack` | Realm to create. |
| `frontend_url` | `http://localhost:3000` | SPA origin: redirect URI, web origin, post-logout `<frontend_url>/login`. |
| `ssl_required` | `none` | Realm SSL mode. |

## Outputs

| Output | Feeds |
|---|---|
| `backend_environment` | Backend `KEYCLOAK_ISSUER_URL`, `KEYCLOAK_AUDIENCES`, `KEYCLOAK_APP_CLIENTS`, `KEYCLOAK_PORTABLE_TYPES`, `KEYCLOAK_ORGANIZATION_BOUND_TYPES`, `KEYCLOAK_PORTABLE_PERMISSIONS`, `KEYCLOAK_REQUIRE_HTTPS`, `KEYCLOAK_POST_LOGOUT_REDIRECT_URI`, `KEYCLOAK_DIRECTORY_CLIENT_ID` ([`docs/environment-variables.md`](../../docs/environment-variables.md)). |
| `keycloak_directory_client_secret` (sensitive) | Backend `KEYCLOAK_DIRECTORY_CLIENT_SECRET`. |
| `frontend_environment` | Frontend `VITE_OIDC_AUTHORITY`, `VITE_OIDC_CLIENT_ID`, `VITE_OIDC_REDIRECT_URI`, one map per app client. |
| `user_ids` | Each user's id (token `sub`). |
| `user_passwords` (sensitive) | Each user's login password. |

## Members added by hand are removed

`keycloak_organization_memberships` is authoritative over an organization's members. A member
added to `acme` or `globex` in the admin console or through the Admin API shows up as a change in
the next `terraform plan`, and the next `terraform apply` removes them. Add members here instead.
`keycloak_user_roles` is authoritative in the same way over each user's roles.

## Keeping it the same as the import

When a change adds a user, client, role, organization or member to the import file, the same
change adds it here. `make keycloak-terraform-check`
([`scripts/check-against-compose.sh`](scripts/check-against-compose.sh)) checks the two against
each other in the compose `keycloak-test` container:

1. deletes any `identity-stack-terraform` realm an earlier killed or failed run left in a
   keycloak-test that is still up, then applies this root to a new realm of that name beside
   the imported `identity-stack`, with its own state in a temporary directory;
2. runs `terraform plan` again and fails unless it is empty;
3. runs [`scripts/check_realm.py`](scripts/check_realm.py), which compares the realm settings,
   clients, client roles, scope mappings, users and their roles, organizations, domains, members
   and `type:` attributes through the Admin API; logs the users in to both realms and compares
   the tokens' `iss`, `aud`, `azp`, `organization`, `resource_access`, `scope` and claim names;
   compares the claim names with [`keycloak/fixtures/access-token.json`](../../keycloak/fixtures/access-token.json);
   fails on any protocol mapper that writes a user attribute or property to `aud`, `azp`,
   `organization`, `resource_access`, `dct` or `tenants`; and reads `bob`'s organizations
   with the directory client's generated secret. Users, organizations and members are read
   one page of `LISTING_PAGE_SIZE` at a time, and a full page fails the check as possibly cut off;
4. destroys the realm (if the destroy fails, the temporary state directory is kept and its
   path printed), and stops the container (deleting its volumes) only if the script started
   it: a keycloak-test that was already running is left up.

It needs Docker, `terraform` and the backend virtual environment
(`cd backend && uv sync --locked --extra dev`). On a Docker host shared with other sessions, hold
the compose lock: `flock ~/.cache/identity-stack-compose.lock make keycloak-terraform-check`.
